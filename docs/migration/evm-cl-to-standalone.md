# Migrating an EVM node operator from CL mode to standalone

A node operator running CCV as jobs on a Chainlink node moves to two standalone processes, a verifier
and an executor, without touching a contract and without a duplicate entry in the Job Distributor.
This document is the procedure. It assumes EVM; other families are standalone from the start and have
nothing to migrate.

The migration is a cutover, not a coexistence period. When it is done the Chainlink node no longer
runs the CCV jobs.

Read the context section once, then work the steps in order. Steps 0 through 6 are the node
operator's, steps 7 and 8 are Chainlink Labs', and step 9 is both. Every step ends with a **Done
when** list, so you can confirm it landed before moving on.

## Context

This section is background: what changes, what does not, and why. It is not part of the procedure.
The procedure starts at [step 0](#step-0-check-how-many-verifier-jobs-the-node-runs-node-operator).

### Before and after

| Component            | CL mode                                            | Standalone                                                                |
|----------------------|----------------------------------------------------|---------------------------------------------------------------------------|
| Onchain signing key  | OCR2 EVM key bundle on the node                    | The same key, imported from the node's export                             |
| Transmitter          | One EVM account per destination chain              | One fresh key, generated by the executor and funded by the operator        |
| CCV jobs             | Two jobs on one node (verifier and executor)       | One job on each of the two processes                                      |
| JD node record       | One record for both jobs                           | Two: the verifier adopts the existing record, the executor registers a new one |
| CSA key              | The node's                                         | Each process generates its own; the JD records are pointed at those        |
| EVM RPC config       | The node's TOML                                    | The same TOML file, read directly                                         |
| Database             | The node's Postgres                                | A bootstrap Postgres database for each process                            |

One key carries over and one does not. The verifier's onchain signing key is preserved, because a
contract depends on it. The executor's transmitter is not: the standalone executor generates a single
fresh key on first boot, and the operator funds it in step 6, the way they fund the node's
transmitters today. The gas that used to sit across the node's per-chain transmitters is where that
funding comes from, so the legacy accounts are the source rather than a leftover.

> To be updated: CCIP-12871 adds a `ccv migrate` command that routes the balances on the node's
> legacy per-chain transmitters to the standalone executor's transmitter, which is what makes step 6
> a single command instead of a manual send per chain. Until it lands, step 6 is done by hand.

### What has to carry over, and why

The **OCR2 EVM key bundle's onchain signing key** is the address in the `CommitteeVerifier` signer
set. The node publishes it to JD as `OnchainSigningAddress`, and that is where the changesets read
each operator's signer from. If you generate a new one, the committee's signer set has to be updated
on every chain, which needs a config transaction per chain and coordination with the other operators
in the committee. This is the one key the export carries.

The standalone verifier keeps publishing it. It declares the chains it signs on in its bootstrap
config, and reports them to JD when it connects, exactly as the node did — for EVM that is not
optional: `ApplyVerifierConfig` and `ApplyExecutorConfig` both check the chain is registered in JD
before they will propose a job spec. So the address is in JD before the cutover and after it, and the
tooling reads it the same way on both sides. `ApplyVerifierConfig` additionally persists the
alias-to-signer mapping into environment state (the `nopSigners` index), which is what covers
families whose standalone verifiers do not report chain configs to JD at all.

The **executor's transmitter** is not carried over. A Chainlink node transmits from an EVM account
per destination chain; the standalone executor holds a single key instead, which it generates itself.
Nothing on chain names the transmitter, so a new account needs no reconfiguration. JD does end up
knowing its address — the bootstrapper publishes the declared secp256k1 key as the signing address on
its own chain configs when it connects, and on the executor that key is the transmitter — but it does
that itself, from the key it generated. Nothing about the transmitter is transcribed or handed over.
The one thing the operator does with it is fund it, in step 6.

The **CSA key** authenticates the node to JD. It carries no on-chain meaning, so it is not exported.
Instead the JD node record is repointed at the standalone verifier's own CSA key, which preserves
the node ID, its name, and its job history while the key stays on the machine that generated it.
This is also why the Chainlink node must be stopped before the standalone verifier starts: JD
identifies a node by the key it authenticates with, and one record cannot have two owners.

The node's **EVM RPC configuration** carries over too, though nothing outside the node depends on
it. Converting it rather than rewriting it is what keeps finality behavior identical across the
cutover; see step 2.

### What you send Chainlink Labs, and what you never send

Chainlink Labs needs two values from you, and nothing else. Both are public keys, and both are copied
verbatim out of a command's output in step 5:

1. The **verifier's CSA public key** — so the operator's existing JD record can be pointed at the
   standalone verifier.
2. The **executor's CSA public key** — so the executor can be registered as a new JD node.

The executor's transmitter is not on that list, and neither is the signing key. The signing key is
imported, so the contract and the jobs are already correct and nothing about it needs sending. The
transmitter address JD does learn, but the executor publishes it itself on connect. The only thing
the operator does with the transmitter is fund it, in step 6.

Why the two CSA keys have to be handed over when nothing else does: JD identifies a node by the CSA
key it authenticates with, and both standalone processes generate their own rather than inheriting the
node's. A process cannot make this change for itself — it cannot authenticate as a record until that
record already carries its key, and the update the bootstrapper does send on connect carries chain
configs only, never a public key. So the record has to be changed on the JD side first, by whoever
holds JD admin. That is the standing cost of not exporting the CSA private key, which is deliberate:
exporting it would copy a private key out of the node and, for as long as both processes held it,
leave two processes able to claim one identity.

Never send, and no part of this procedure asks for:

- Any private key, including the CSA private key. "CSA key" in this document always means the CSA
  *public* key.
- `ocr2.json`, the export from step 1. It is the verifier's own signing key, encrypted. It goes into
  your verifier's container and nowhere else.
- `export-password.txt`, the password that export is encrypted under.
- The node's API credentials file.

If a request asks you for any of those, it is not this procedure.

### One record becomes two

In CL mode a single JD node record runs both the `ccvcommitteeverifier` and `ccvexecutor` jobs. In
standalone those are two processes with two keystores, so they need two records. The verifier adopts
the operator's existing record, keeping the NOP alias that `ApplyVerifierConfig` and
`fetch_signing_keys` look up by. The executor registers a new one.

That second record is a property of standalone mode, not of the migration: an operator who had
started standalone would have had two from the beginning. What the migration avoids is a *duplicate*
— the operator's existing record is reused for the verifier rather than abandoned next to a new one.

The two processes differ in what they carry across. The verifier imports the node's signing key, so
its identity is preserved. The executor does not import anything: it generates a fresh transmitter
key that the operator funds, one account instead of the node's per-chain transmitters. This is the
single-key executor a live deployment runs, brought up per operator as part of the cutover.

## Who does what

Steps 0 through 6 are the node operator's: check the job shape, export the signing key, configure and
start the standalone verifier and executor, stop the Chainlink node along the way, and fund the
executor's transmitter. Within those, the node is stopped in step 4 and the standalone processes are
started in step 5, in that order.

Steps 7 and 8 are on the Chainlink Labs side, because JD and the topology are centrally operated:
repointing the verifier's JD record, registering the executor, flipping the topology, proposing the
standalone specs. Step 9 is confirmed by both.

That split is also the safety net. Each operator's signing address is read from JD before the cutover,
while the Chainlink node still owns the record, and required to be unchanged afterwards — the
assertion `TestE2EMigration_CLToStandalone` makes. The pre-cutover read has to happen first because
the record changes hands in step 7, not because the address stops being published: the standalone
verifier reports it again once it connects.

A mistake in the operator's steps therefore surfaces centrally, before any job moves, in two places:
the verifier changeset wants to change the committee's signer set when it should be a no-op, or it
refuses to propose at all because the chain is not registered in JD for that operator.

## Before you start

Have ready:

- The Chainlink node's API credentials, in a file with the email on line 1 and the password on
  line 2 — the layout `chainlink admin login --file` reads. The export tool uses them, and the
  export endpoints need the node's admin account.
- A Postgres database for each standalone process. The verifier and executor each need their own
  bootstrap database, separate from any application database. Create them empty and hand each process
  a connection string: the schema is created on first boot and left alone on every boot after, so
  there is nothing to migrate by hand.
  > To be updated: when the EVM standalone gains persistence it will need a database of its own on
  > top of the bootstrap one. It does not have to be a separate Postgres server, but it is a separate
  > database, so the count here will change.
- The Chainlink node's TOML configuration file.
- The verifier and executor images you are about to deploy. The export tool ships in the verifier
  image as `ccv migrate`, so there
  is nothing separate to install.

## Step 0: check how many verifier jobs the node runs (node operator)

A standalone process runs a single job, so this procedure applies to a node running one
`ccvcommitteeverifier` job.

```sh
chainlink jobs list
```

If the node runs more than one verifier job, stop and raise it with Chainlink Labs before going
further. That happens when the committee's job specs are still generated per aggregator, which is a
property of how Chainlink Labs runs the aggregators and generates job proposals — nothing a node
operator configures or can change. It has to be resolved on that side first, by consolidating the
committee's verifier jobs into one that writes to every aggregator, and only then does this
procedure apply. Existing credentials survive that change: a consolidated job reuses the
per-aggregator `verifier_id` as each aggregator's credential lookup key, so nothing is
re-provisioned.

Step 1 runs this same check itself and stops with an error rather than picking one of the jobs
arbitrarily, so this step is a chance to find out before you start rather than a gate you can skip
past.

**Done when:**

- `chainlink jobs list` shows exactly one `ccvcommitteeverifier` job on the node.
- It also shows the `ccvexecutor` job, which confirms this is the node running this operator's CCV
  jobs and not another one.

## Step 1: export the signing key (node operator)

Run the export tool from the verifier image. It finds the OCR2 bundle registered for EVM — the same
source the node's JD chain config was built from, so nothing is transcribed and nothing is guessed —
exports it under a generated password, and verifies the file decodes to the identity the node
registered, while the node is still up to correct a mistake:

```sh
docker run --rm --network host -v "$PWD/migration:/out" <verifier-image> \
  ccv migrate export \
    --node-url http://localhost:6688 \
    --api-creds /out/api-creds.txt \
    --out-dir /out
```

`--network host` lets the container reach a node API on the host's `localhost`; if the node's API
is reachable at another address, point `--node-url` at it instead. The credentials file sits in the
mounted directory so the container can read it.

The tool runs the step 0 check itself and stops with an error on a node running more than one
verifier job, rather than picking one. It also stops if the node has several EVM OCR2 bundles; in
that case take the right one from the JD node record — never from a guess — and pass it as
`--bundle-id`.

What it writes into the output directory:

- `ocr2.json` — the export, mode 0600.
- `export-password.txt` — the generated password, mode 0600.
- `verifier.key_import.toml` — the `[key_import]` block for the verifier, with `expected_id` already
  filled in from the export. Do not retype the address.

The manual equivalent — `chainlink keys ocr2 list` and `export` — still works if the tool cannot
reach the node. If you use it, take the address for `expected_id` from the JD node record, not from
the list output you happened to pick: the whole point of the check is that it disagrees with a wrong
choice.

**Done when:**

- The command exited 0 and printed a signing address.
- All three files above are in the output directory, and the two secrets are mode 0600.
- The printed signing address matches the `OnchainSigningAddress` on the operator's JD node record.
  If it does not, stop: the export is of the wrong bundle, and every later step inherits that.

## Step 2: reuse the node's RPC configuration (node operator)

There is nothing to convert. Mount the Chainlink node's own TOML config file at the verifier's EVM
config path and it is read directly: the `[[EVM]]` and `[[EVM.Nodes]]` sections are translated at
startup, chain IDs are resolved to chain selectors, and every other section in the file is ignored.

Finality carries over as the node had it. The node's own chain defaults are applied before
translating, so a chain you never configured explicitly keeps the behavior it had rather than
quietly moving onto finality tags.

A few things a Chainlink node can express have no standalone equivalent and are dropped: send-only
nodes, and per-node `Order`, `HTTPURLExtraWrite` and `IsLoadBalancedRPC`. Each one is logged at
startup saying exactly what was dropped. If you rely on a send-only endpoint, add it as a full node.

> To be updated: per-node `Order` is being added to the standalone accessor. Once it lands it will
> carry over instead of being dropped, and it comes off this list. Until then, a node that relies on
> RPC ordering loses it across the cutover.

**Done when:**

- The same TOML file the Chainlink node runs with is mounted at the verifier's and the executor's EVM
  config path. Nothing has been edited or rewritten.
- Nothing else to check here until step 5: the file is read at startup, so the translation is
  confirmed from the startup log there.

## Step 3: configure the standalone verifier to adopt the key (node operator)

Step 1 wrote the block the verifier needs. Mount `ocr2.json` and the password file into the
verifier's container at the paths the snippet names — renaming the key file to `key.json` on the
way in — and add the snippet's `[key_import]` block to the bootstrap config:

```toml
[key_import]
path          = "/etc/ccv/migration/key.json"
password_path = "/etc/ccv/migration/export-password.txt"
expected_id   = "0x..."
```

Two paths and one check. You do not say which keystore key the file becomes, because the verifier
has exactly one it can import into, and you do not say which export it is, because that is read from
the file.

`expected_id` is the signing address from step 1, written into the snippet by the tool. It is
required — the bootstrapper refuses to start without it — because it is the check that fails the boot
when the wrong node's export is mounted: without it the process comes up signing with another
operator's key, which produces verification results the committee rejects with nothing in the logs
pointing at the cause. The tool already wrote it, so paste the block as generated and do not retype
the address.

Before starting the verifier, confirm the mounted file reads back as the right identity without
booting anything:

```sh
ccv migrate inspect \
  --key-file /etc/ccv/migration/key.json \
  --password-file /etc/ccv/migration/export-password.txt
```

The import runs only when the key is absent, so it is a no-op on every restart after the first. Once
the verifier has come up once, unmount the export and the password file and delete them.

The executor needs no `[key_import]`. It generates its own transmitter key on first boot, which you
fund in step 6; give it its bootstrap config and the same mounted node TOML from step 2, and nothing
else.

**Done when:**

- `ccv migrate inspect` prints the same address as `expected_id` in the config, and the same address
  step 1 printed.
- The verifier's bootstrap config has the `[key_import]` block, with all three fields set.
- The executor's bootstrap config has no `[key_import]` block.

## Step 4: stop the Chainlink node (node operator)

Stop it before starting the standalone verifier. The verifier is about to take over its JD record,
and while the node is connected the two contend for it.

The hard deadline is the repoint in step 7: the node has to be down before its JD record changes
hands, which is before any standalone job is sent. Stopping it here, before the standalone processes
start, is what keeps the window where no one serves the lane short and removes any doubt about
which process owns the record.

Stopping the node ends CL mode for this operator. Both CCV jobs ran on the one node, so it cannot
serve one of them while the other migrates; the standalone verifier and executor take over the lane
once they are up.

Pick a quiet moment if you can. The standalone executor reads each message's on-chain execution
state before it executes, so anything the node already landed is skipped. The gap is a transaction
the node submitted that has not confirmed yet: the state read still says unexecuted, so the
standalone executor can submit its own attempt, from its own account, for the same message. One of
the two lands and the other reverts, so this costs a wasted transaction rather than a double
delivery — but a drained queue is cleaner than a raced one.

**Done when:**

- The node's API no longer answers on `--node-url`.
- JD shows the operator's node record as disconnected.
- The node's CCV job runs have stopped advancing. It stays stopped from here until step 9, or until
  a rollback.

## Step 5: start the standalone processes (node operator)

Start the verifier and the executor. The verifier generates its own CSA key on first boot and imports
the signing key you declared; the executor generates its own CSA and transmitter keys.

Then read the CSA public key off each process's info server. The port is the one you set as
`listen_port` in the bootstrap config's `[server]` section; 9988 is the value used throughout this
document. Run this against the verifier and again against the executor:

```sh
curl -s -X POST localhost:9988/keystore/reader/getkeys \
  -d '{"KeyNames":["bootstrap_default_csa_key"]}'
```

The response is `{"Keys":[{"KeyInfo":{"Name":...,"PublicKey":...}}]}`. `PublicKey` is base64 in that
JSON; send the value exactly as it comes back, without re-encoding it.

Those two CSA public keys go to Chainlink Labs, labeled by which process each came from. Nothing
else, and nothing private — see [what you never
send](#what-you-send-chainlink-labs-and-what-you-never-send).

You do not need to read any address out of a key here. The executor logs its own transmitter address
for step 6, and the verifier's imported signing key is checked against `expected_id` on boot: the
process refuses to start if the key it imported, or the key already in its keystore, is not the
address you pinned. Reaching a healthy state is the confirmation.

**Done when:**

- Both processes are up and healthy, and neither is restarting.
- The verifier's startup log shows the key import succeeded, and no `expected_id` mismatch.
- The startup log lists every chain you expect from the step 2 TOML, and you have read the
  dropped-setting warnings and accept each one.
- You have both CSA public keys and have sent them to Chainlink Labs.

## Step 6: fund the executor's transmitter (node operator)

The executor transmits from the single key it generated in step 5, and that key holds nothing until
you fund it. Fund it on every chain the executor transmits on, from the gas that used to sit on the
node's per-chain transmitters. Do this before the job specs are proposed in step 8, so the executor
can submit the moment it gets work.

The executor prints the address to fund on startup. It generated the key, so it derives the address
itself — copy it out of the log rather than computing anything:

```sh
docker logs <executor-container> | grep evm/tx/executor_evm_transmitter_key
```

The line is the `key created` (first boot) or `key already exists` (every boot after) entry for that
key name, and `evmAddress` on it is the address, EIP-55 checksummed. That is the only place you need
to read it from, and it is stable across restarts because the key is generated once.

> To be updated: CCIP-12871 adds the `ccv migrate` command that does this step end to end — it reads
> the transmitter address and routes the balances from the node's legacy per-chain transmitters into
> it, so the operator sends nothing by hand. Until it lands, the sends are manual.

**Done when:**

- The address from the executor's `evmAddress` log field holds a non-zero balance on every chain the
  executor transmits on, enough for the execution volume this operator carries.
- You confirmed each balance by reading the address on chain, not by assuming the send succeeded.
- The log line you took the address from is this operator's executor, not another operator's.

## Step 7: hand the JD record to the verifier and register the executor (Chainlink Labs)

Using the two CSA public keys from step 5:

1. Repoint the operator's existing JD node record at the verifier's CSA public key, keeping the node
   ID and the NOP alias.
2. Register the executor as a new JD node under its own name and the executor's CSA public key.

Wait for JD to report both as connected before proposing jobs. A proposal sent to a record whose new
owner has not dialed in yet sits unclaimed.

**Done when:**

- The operator's existing JD record has the verifier's CSA public key, and the same node ID and NOP
  alias it had before.
- A second JD record exists for the executor, with the executor's CSA public key.
- Both records report connected.

## Step 8: propose the standalone job specs (Chainlink Labs)

1. Set the operator's mode to `standalone` in the topology.
2. Re-run `ApplyVerifierConfig` and `ApplyExecutorConfig`. The two modes differ in one field: a
   CL-mode spec carries the app config under `committeeVerifierConfig` and `executorConfig`, a
   standalone spec under `appConfig`. Proposing the standalone specs replaces the CL-mode ones, and
   the previous proposals are revoked.

Because the signing address did not change, the verifier changeset produces no contract transaction.
If it proposes one, the imported key is not the one the committee has registered; stop and re-check
step 1.

**Done when:**

- `ApplyVerifierConfig` produced no contract transaction. This is the check that matters: a signer
  change here means the address the verifier imported is not the one the committee has.
- The signing address JD holds for this operator, now reported by the standalone verifier, is the one
  its record carried before the cutover.
- Both standalone records show an accepted job proposal, and the CL-mode proposals are revoked.

## Step 9: confirm and clean up (both)

1. Send a message across a lane this operator verifies, and confirm it is verified and executed.
2. Confirm on chain that the committee's signer set for this operator is unchanged. The executor's
   transmitter is a new funded account by design, so that one is expected to differ from the node's.
3. Node operator: remove the CCV job specs from the Chainlink node.
4. Node operator: delete `ocr2.json` and `export-password.txt` from wherever you staged them, and
   unmount them from the verifier if you have not already.

**Done when:**

- A message on this operator's lane was verified and executed after the cutover.
- The committee's signer set for this operator is byte-for-byte what it was before.
- The Chainlink node holds no CCV job specs.
- The export and the password file are gone from the host and from the verifier's mounts, and the
  verifier still starts without them.

## If it goes wrong

Up to step 4 nothing has changed: the Chainlink node is still running its jobs, and the standalone
processes are not registered anywhere. Delete the export and stop.

After step 4 the way back is to restart the Chainlink node, repoint the JD record at its CSA public
key, and re-propose the CL-mode specs. The key the standalone verifier imported is a copy, so the
node's own keystore is untouched and it can resume signing and transmitting as before. The executor's
own JD record is discarded. Do this only with the standalone verifier stopped, for the same reason
step 4 exists.

If you had already funded the executor's transmitter in step 6, that gas is still sitting on that
address. Keep the executor's keystore, or its bootstrap database, until you have moved the balance
back — discarding the key discards access to it.

One trap has no clean undo and is easier to avoid than to hit: a verifier that came up once
*without* `[key_import]` has already generated its own signing key, and the import is a no-op while a
key with that name exists. Adding `[key_import]` afterwards does not fix it — `expected_id` is
checked against the key already in the keystore, so the process now refuses to start because the
generated key is not the pinned one. If nothing has registered with JD yet, the fix is to delete the
verifier's bootstrap database and let it recreate the schema, and the import, on the next start. If
registrations already happened, sort the keystore out with Chainlink Labs rather than deleting your
way deeper.

## What is not covered

An operator whose signing key is in an HSM or KMS cannot export it, so this procedure does not apply.
That case needs a new signing key and a committee signer-set update on every chain. Plan it with the
committee rather than as a unilateral migration.

Step 6 funds the standalone transmitter but does not automatically empty the node's per-chain
transmitters. A Chainlink node transmits from an EVM account per destination chain; the standalone
executor replaces all of them with the one key it generated. Once you have funded that key, whatever
is left on the old accounts is yours to sweep on your own schedule, and this procedure does not do it
for you. CCIP-12871 is the command that will (see step 6).
